本课已落地为可运行代码：src/speculative.rs（与第 35 课共用；单测跑 cargo test speculative，数量以实际输出为准）+ speculative 子命令—— 草稿→验证循环、拒绝采样与残差分布修正、TargetStream 的缓存不变量、被拒位置的 rollback_to 对齐。 与已有代码的衔接：复用 src/sample.rs 的整套采样预处理和 src/attention.rs 的 KV Cache； 草稿模型直接用 src/model.rs 的 Transformer 结构（ModelDrafter）。

1. 推理瓶颈：自回归的根本问题

LLM 生成文本是逐 token 自回归的——每生成一个 token 都要跑一次完整的前向传播。

输入: "The cat"
Step 1: 模型前向 → "sat"
Step 2: 模型前向 → "on"
Step 3: 模型前向 → "the"
Step 4: 模型前向 → "mat"

每一步都是一个内存带宽瓶颈（memory-bound）操作——需要把数十 GB 的权重从显存读到计算单元，但实际计算量很小（只算一个 token）。GPU 的算力利用率极低（通常 < 5%）。

核心矛盾：大模型的单 token 推理是 memory-bound，GPU 算力闲置；batch 推理虽然能提高利用率，但交互式场景（聊天、代码补完）只能逐 token 生成。

2. 推测解码的核心思想

用一个小而快的"草稿模型"（Draft Model）一次性猜出多个 token，再用大模型一次性验证。

传统方式（5 次大模型前向）：
  大模型 → token1
  大模型 → token2
  大模型 → token3
  大模型 → token4
  大模型 → token5

推测解码（1 次小模型 + 1 次大模型）：
  小模型快速猜 → token1, token2, token3, token4, token5
  大模型一次性验证 → 接受 token1, token2, token3; 拒绝 token4,5 → 大模型自己补 token4'

收益：如果小模型猜对了 K 个 token，大模型只需一次前向传播就"生成"了 K 个 token。

3. 数学保证

推测解码最关键的设计是：它的输出分布与纯大模型自回归采样完全一致（无损）。

3.1 验证算法

设大模型概率为 $p(x_t|x_{<t})$，小模型概率为 $q(x_t|x_{<t})$：

对于草稿模型猜的 token $\hat{x}_t$：

  1. 接受概率： $$ \text{accept_prob} = \min\left(1, \frac{p(\hat{x}t | x{<t})}{q(\hat{x}t | x{<t})}\right) $$

  2. 如果拒绝：从修正分布中重新采样： $$ x_t \sim \text{norm_max}\left(p(x_t | x_{<t}) - q(x_t | x_{<t})\right) $$

其中 $\text{norm_max}(z) = \frac{\max(z, 0)}{\sum_i \max(z_i, 0)}$。

直觉：

  • 如果大模型认为这个 token 的概率比小模型还高（$p/q \geq 1$），一定接受
  • 如果大模型认为概率偏低（$p/q < 1$），以 $p/q$ 的概率接受
  • 拒绝时，从"大模型认为好但小模型没猜到"的分布中重新采样

3.2 为什么无损？

这本质上是对**拒绝采样（Rejection Sampling）**的巧妙应用：

  • 接受时，分布是 $q$ 加上 $p$ 的截断——数学上恰好等于 $p$
  • 拒绝时，从 $p-q$ 的残差分布中采样——补回了 $q$ 低估的部分
  • 两者合并，最终采样分布严格等于 $p$

4. 实现框架

┌─────────────┐
│  草稿模型 q  │ ← 小模型（如 LLaMA-68M 或模型本身的前几层）
└──────┬──────┘
       │ 快速猜 K 个 token
       │ [t1, t2, t3, t4, t5]
       ▼
┌─────────────┐
│  大模型 p    │ ← 完整模型（如 LLaMA-70B）
└──────┬──────┘
       │ 一次前向传播，同时计算 K 个位置的 logits
       │ 逐个验证：接受/拒绝
       ▼
  接受 [t1, t2, t3] + 大模型补充 t4'
  共生成 4 个 token，但只用了 1 次大模型前向

4.1 关键实现细节

1. KV Cache 同步

大模型验证时需要一次性处理 K 个 token，KV Cache 需要：

  • 验证前：追加草稿模型猜的 K 个 token 的 K/V
  • 接受 n 个后：保留前 n 个，丢弃后面的
  • 下一轮：从第 n+1 个 token 开始新的草稿
草稿阶段: KV = [已有历史] + [draft1, draft2, draft3, draft4, draft5]
验证结果: 接受 3 个
保留:     KV = [已有历史] + [draft1, draft2, draft3]  // 丢弃 4,5
大模型补:  KV = [已有历史] + [draft1, draft2, draft3] + [大模型输出]

2. 草稿模型的选择

方案 说明 优缺点
独立小模型 训练/蒸馏一个同架构的小模型 需要额外模型；接受率高
浅层推测 用大模型的前 N 层作为草稿模型 无需额外模型；接受率中等
N-gram 预测 用 N-gram 统计模式猜 极快；接受率低
Medusa（2024） 在大模型上加多个预测头 一次前向猜多个 token；需要训练头
EAGLE（2024） 用特征级别的草稿模型 接受率最高；实现较复杂

3. 批量验证优化

大模型验证 K 个 token 时，可以用 tree attention 替代线性验证——同时验证多条分支路径：

              root
            /      \
         t1_a      t1_b
        /    \        \
     t2_a   t2_b     t2_c

树结构让一次大模型前向就能验证多条候选路径，进一步提高接受率。

5. 性能分析

5.1 理论加速比

设：

  • 大模型单步延迟：$T_{\text{large}}$
  • 小模型单步延迟：$T_{\text{draft}}$
  • 接受率：$\alpha$（平均每步猜对的比例）
  • 猜测长度：$K$

平均每次验证生成的 token 数： $$ \mathbb{E}[\text{tokens}] = \frac{1 - \alpha^{K+1}}{1 - \alpha} $$

总延迟：$K \cdot T_{\text{draft}} + T_{\text{large}}$

加速比： $$ \text{Speedup} = \frac{\mathbb{E}[\text{tokens}] \cdot T_{\text{large}}}{K \cdot T_{\text{draft}} + T_{\text{large}}} $$

5.2 实际效果

设置 加速比 说明
LLaMA-70B + LLaMA-7B 草稿 2~3× 接受率约 70-80%
LLaMA-70B + 68M 草稿 1.5~2× 草稿太快但接受率低
Medusa（无需额外模型） 2~2.5× 需要额外训练多头
EAGLE-2 3~4× 目前最快的方案之一

6. 与其他加速方法的对比

方法 原理 是否无损 适用场景
推测解码 小模型猜 + 大模型验 无损 延迟敏感的交互场景
量化 减少权重精度 有损（微小） 显存/带宽受限
KV Cache 缓存历史 K/V 无损 已是标配

7.1 代码结构

组件 位置 说明
SpecStats speculative.rs 统计口径：轮次、草稿数、接受数、拒绝修正数、白拿 token 数、目标前向次数；提供 acceptance_rate() 和 tokens_per_forward()
Proposal speculative.rs 一个草稿候选：token id + 支撑集 ids + 对应概率分布 q（供拒绝采样使用）
Drafter trait speculative.rs 草稿来源的统一接口：propose()（提出 γ 个候选）、commit()（对齐内部状态）、reset()
TargetStream speculative.rs 单序列增量前向句柄：维护 KV cache，保持"缓存落后序列一格"的不变量；提供 feed/feed_hidden/sync/rollback_to/reset
SpecDecoder speculative.rs 推测解码执行体：持有目标模型缓存与统计，核心方法 step() 每轮让草稿提出候选→目标一次前向并行验证，返回 1~γ+1 个 token
ModelDrafter speculative.rs 草稿来源一：用另一个自回归模型按自己的分布猜 γ 个 token，支持 greedy 模式
MtpHeads speculative.rs 多 Token 预测头（第 35 课）：K 个 Linear 层，第 k 个头把位置 i 的隐状态映射到 i+k+1 的 logits；loss() 计算各头交叉熵之和的均值
MtpDrafter speculative.rs 草稿来源二：拿 MTP 头当草稿，一次前向给出往后 γ 个位置的候选分布（不必自回归），但各分布彼此条件独立，接受率通常更低
speculative_generate speculative.rs 文本生成入口：接收目标模型、分词器、prompt、gamma、采样选项、草稿器，返回 (生成文本, 统计)

7.2 CLI 用法

# 基本推测解码（γ=4 草稿 + 目标验证，默认 prompt "the key opens"）
cargo run --release -- speculative

# 调整草稿候选数和生成长度
cargo run --release -- speculative --gamma 6 --max-new 64

# 自定义 prompt
cargo run --release -- speculative --prompt "once upon a time"

# MTP 头草稿（训练 MTP 头后用于推测解码）
cargo run --release -- speculative --mtp-heads 4 --mtp-steps 80

# 调整温度和模型规模
cargo run --release -- speculative --temperature 0.9 --n-embd 64 --n-layer 4

8. 小结与下一课

本课小结

  • 自回归逐 token 生成是 memory-bound 的：GPU 算力闲置，瓶颈在搬权重
  • 推测解码用"小模型一次猜 γ 个 + 大模型一次验证"把多次前向压成一次
  • 无损性有严格数学保证：接受概率 min(1, p/q) + 拒绝时从 norm_max(p − q) 残差分布重采样，合并后分布严格等于 p
  • 加速比取决于接受率与草稿成本；本仓库的落点是 src/speculative.rs 的草稿→验证循环、TargetStream 的缓存不变量与 rollback_to 对齐
  • 与量化（省带宽）、KV Cache（免重算）、批量推理（提吞吐）是不同维度的加速手段，见 §6 的对比表

拓展方向

核心内容已全部实现（src/speculative.rs + speculative 子命令），这里是进阶拓展。

  1. 理解拒绝采样：实现一个简单的拒绝采样器，从目标分布 $p$ 中采样，只使用提议分布 $q$ 和均匀随机数。
  2. 模拟推测解码：用两个不同大小的概率分布模拟大/小模型，实现推测解码的接受/拒绝逻辑，验证输出分布是否等于大模型分布。
  3. KV Cache 同步：设计数据结构，支持推测解码中的"追加 → 验证 → 保留/丢弃"操作。
  4. 接受率实验：用不同温度采样时，推测解码的接受率如何变化？为什么温度越低接受率越高？
