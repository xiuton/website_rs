第 37 课：RAG 检索增强生成（Retrieval-Augmented Generation）

本课已落地为可运行代码：src/rag.rs（单测跑 cargo test rag，数量以实际输出为准）+ rag 子命令——分块（字符域切分 + 句读对齐 + 可配重叠）、三种向量化（TF-IDF / FNV 哈希 / 模型隐状态池化）、余弦检索与 MMR 多样化重排、提示组装。 与已有代码的衔接：生成阶段复用 src/sample.rs 的 generate；稠密向量由 Transformer::forward_hidden 做均值池化得到，余弦相似度在 L2 归一化后用点积计算。

1. LLM 的知识局限

大语言模型通过预训练"记住"了大量知识，但存在根本性问题：

问题 说明 示例
知识截止 训练数据有时间边界 "2024年美国大选结果？"
幻觉 编造不存在的事实 虚假的论文引用、不存在的API
无法访问私有数据 不知道企业内部文档 "我们公司的报销流程？"
长尾知识 低频领域知识不准确 特定法律条文、技术细节

2. RAG 的核心思想

不要让模型"凭记忆回答"，而是先检索相关文档，再根据文档回答。

用户提问: "公司2024年Q3的营收是多少？"
          │
    ┌─────▼─────┐
    │ 检索系统   │ ← 在公司财报文档中搜索
    └─────┬─────┘
          │ 检索到: "2024年Q3营收58.3亿元，同比增长12%..."
    ┌─────▼─────┐
    │ LLM 生成   │ ← 基于检索到的文档生成回答
    └─────┬─────┘
          │
回答: "公司2024年Q3营收为58.3亿元，同比增长12%。"

3. RAG 架构详解

3.1 整体流程

离线阶段（索引构建）:
  文档集合 → 分块(Chunking) → 向量化(Embedding) → 向量数据库

在线阶段（查询）:
  用户问题 → 向量化 → 相似度检索 Top-K → 拼接上下文 → LLM 生成回答

3.2 文档分块（Chunking）

长文档需要切分成小块（chunks），因为：

  • Embedding 模型有最大长度限制（通常 512~8192 tokens）
  • 太大的块会稀释关键信息
分块策略 说明 适用场景
固定长度 按 token/字符数切分 简单通用
按段落/章节 按自然分隔符切分 结构化文档
滑动窗口 有重叠的切分（overlap） 避免信息被截断
语义分块 按语义相似度切分 精度最高但计算量大 
典型设置:
  chunk_size = 512 tokens
  chunk_overlap = 50 tokens  // 前后块有 50 token 重叠，避免边界信息丢失

3.3 向量嵌入（Embedding）

把文本块转化为高维向量，使得语义相似的文本在向量空间中距离近。

"如何退款？" → [0.12, -0.34, 0.56, ..., 0.78]  (768维)
"退款流程是什么？" → [0.11, -0.33, 0.57, ..., 0.79]  (距离很近)
"今天天气怎么样？" → [-0.45, 0.67, -0.12, ..., 0.23]  (距离很远)

常用 Embedding 模型：

模型 维度 说明
text-embedding-ada-002 (OpenAI) 1536 商用，效果好
BGE-large (BAAI) 1024 开源，中英文优秀
E5-large-v2 (Microsoft) 1024 开源
GTE-large (Alibaba) 1024 开源
nomic-embed-text 768 轻量开源

3.4 向量检索

在向量数据库中找到与问题向量最相似的 Top-K 个文档块。

相似度度量

余弦相似度（最常用）： $$ \text{sim}(a, b) = \frac{a \cdot b}{||a|| \cdot ||b||} $$

L2 距离： $$ d(a, b) = ||a - b||_2 $$

内积（向量已归一化时等价于余弦相似度）： $$ \text{sim}(a, b) = a \cdot b $$

ANN（近似最近邻）搜索

精确搜索在百万级文档上太慢，实际使用近似算法：

算法 原理 说明
HNSW 分层可导航小世界图 精度高速度快，主流方案
IVF 倒排索引 + 聚类 适合大规模数据
PQ 乘积量化压缩向量 节省存储空间
ScaNN 各向异性量化 Google 出品

3.5 上下文拼接与生成

检索到 Top-K 个相关块后，拼接成 Prompt 发给 LLM：

Prompt 模板:
"""
根据以下参考资料回答问题。如果资料中没有相关信息，请说"我无法从提供的资料中找到答案"。

参考资料:
[1] {chunk_1}
[2] {chunk_2}
[3] {chunk_3}

问题: {user_question}

回答:
"""

4. 高级 RAG 技术

4.1 Query 变换（Query Transformation）

用户的原始问题可能不适合直接检索，需要变换：

  • 查询扩展（Query Expansion）：把一个问题拆成多个子问题分别检索
  • HyDE（Hypothetical Document Embeddings）：先让 LLM 生成一个"假设性答案"，用答案的向量去检索（因为答案和文档的语义更接近）
  • Step-Back Prompting：先问一个更抽象的问题，再检索

4.2 重排序（Re-ranking）

向量检索是粗筛，结果可能不精确。用一个**交叉编码器（Cross-Encoder）**对 Top-K 结果重新打分：

向量检索 Top-20 → Cross-Encoder 重排序 → 取 Top-3 → 送入 LLM

4.3 多跳推理（Multi-hop RAG）

复杂问题需要多步检索：

问题: "写《百年孤独》的作者的出生地在哪个国家？"

Step 1: 检索 "《百年孤独》的作者" → 加西亚·马尔克斯
Step 2: 检索 "加西亚·马尔克斯 出生地" → 哥伦比亚阿拉卡塔卡
回答: 哥伦比亚

4.4 自适应检索（Self-RAG，2023）

LLM 自己决定是否需要检索、检索结果是否有用：

LLM 判断: "这个问题我确定知道" → 直接回答
LLM 判断: "这个问题我不确定" → 触发检索
检索后判断: "这个结果相关" → 用于生成
检索后判断: "这个结果不相关" → 重新检索或直接回答

5. 向量数据库

数据库 类型 特点
FAISS 库（Meta） 高性能，本地使用
Chroma 轻量数据库 简单易用，适合原型
Weaviate 云原生数据库 支持混合搜索
Milvus 分布式数据库 大规模生产环境
Pinecone 云服务 全托管，零运维
Qdrant Rust 实现 高性能，Rust 生态

6. RAG 的评估

指标 评估什么 计算方式
检索精度（Recall@K） Top-K 中包含正确文档的比例 正确文档数 / 总正确文档数
检索排序（MRR） 正确文档排在第几位 1 / 排名
生成忠实度（Faithfulness） 回答是否忠于检索到的文档 LLM-as-Judge
回答正确性（Correctness） 回答是否正确 与标准答案对比

7. RAG vs 微调 vs 长上下文

方案 适用场景 优势 劣势
RAG 知识频繁更新、需要引用来源 知识可实时更新、可解释 检索质量影响大
微调 特定领域风格、格式要求 回答质量高、延迟低 知识不可实时更新
长上下文 文档数量少（< 100K tokens） 实现简单 成本高、长文本质量下降

最佳实践：三者常组合使用——RAG 提供外部知识，微调适应领域风格，长上下文处理单篇长文档。

8. 本仓库实现要点

上面的原理已全部落地为可运行代码。核心文件是 src/rag.rs（单测跑 cargo test rag，数量以实际输出为准）， CLI 入口是 rag 子命令。

8.1 代码结构

组件 位置 说明
ChunkOpts / Chunk rag.rs 分块参数（size/overlap/align）与文本块（text/start/end/source）
chunk_text rag.rs 将长文本按字符窗口切成带重叠的块，支持可选的句子/段落边界对齐
Embedder trait rag.rs 向量化器接口：dim() + embed(text) → Vec<f32>
TfIdf rag.rs TF-IDF 向量化器：fit 统计文档频率，embed 生成稀疏向量
HashingEmbedder rag.rs 特征哈希向量化器：FNV-1a 哈希映射到固定维度，无词表、无未登录词问题，符号哈希缓解冲突偏置
ModelEmbedder rag.rs 模型稠密向量化器：Transformer 隐状态均值池化 + 归一化，三者中唯一"懂语义"的检索器
ScoredChunk rag.rs 一条检索结果：index + chunk + 余弦相似度 score
Retriever rag.rs 向量检索器：持有嵌入器 + 块向量，提供 build/from_text/from_corpus_dir/search（暴力 top-k）/search_mmr（MMR 去冗余重排）
PromptOpts / RagPrompt rag.rs 提示组装参数与结果：字符预算 max_context_chars + 系统约束指令 + 来源标注
build_rag_prompt rag.rs 将检索命中组装为最终提示文本，带来源标注和字符预算裁剪，强制"只依据资料回答"
l2_norm / l2_normalize / cosine_similarity rag.rs 底层向量工具：L2 范数、归一化、余弦相似度（零向量安全）
truncate_chars / terms rag.rs 文本工具：按字符截断（中文安全）、unigram+bigram 词项切分（无分词器的中文检索）

8.2 CLI 用法

# 默认配置（chunk_size=120, overlap=30, top_k=4, 特征哈希 512 维）
cargo run --release -- rag

# 调整分块参数
cargo run --release -- rag --chunk-size 200 --overlap 50

# 调整检索参数
cargo run --release -- rag --top-k 6 --mmr-lambda 0.3 --mmr-pool 20

# 自定义查询
cargo run --release -- rag --query "attention mechanism transformer"

# 使用模型稠密向量（需要先训练小模型）
cargo run --release -- rag --n-embd 64 --n-layer 4

# 调整提示预算
cargo run --release -- rag --context-chars 500

9. 小结与下一课

本课小结

  • RAG 解决的是"模型不知道/记不准/不能查私有数据"这件事：先检索，再根据检索到的资料回答
  • 离线阶段：分块（固定长度 / 段落 / 滑动窗口 / 语义）→ 向量化 → 建向量库；在线阶段：查询向量化 → Top-K 检索 → 拼上下文 → 生成
  • 三种相似度（余弦 / L2 / 内积）在向量归一化后等价；百万级文档要用 HNSW / IVF / PQ 这类 ANN 索引
  • 高级技术都在补"召回的精度"：Query 变换（扩展 / HyDE / Step-Back）、Cross-Encoder 重排、多跳检索、自适应的 Self-RAG
  • 评估要同时看检索侧（Recall@K、MRR）与生成侧（Faithfulness、Correctness）；RAG 与微调、长上下文是互补而非替代关系
  • 本仓库把整条链路落地为 src/rag.rs + rag 子命令：三种向量化（TF-IDF / FNV 哈希 / 模型隐状态池化）、暴力 top-k 与 MMR 去冗余重排、带字符预算的提示组装

拓展方向

核心内容已全部实现（src/rag.rs + rag 子命令），这里是进阶拓展。

  1. 实现简单向量检索：给定一组文本的向量表示和一个查询向量，实现余弦相似度 Top-K 检索。
  2. 文本分块：实现滑动窗口分块算法，支持配置 chunk_size 和 overlap。
  3. Prompt 拼接：实现 RAG 的 Prompt 模板，把检索结果和用户问题拼接成完整的输入。
  4. 端到端 RAG：结合前面的 LLM，实现一个简单的 RAG 系统——加载文档、分块、向量化、检索、生成。
