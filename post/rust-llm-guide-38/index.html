第 38 课：分布式训练（Distributed Training）

本课已落地为可运行代码：src/distributed.rs（单测跑 cargo test distributed，数量以实际输出为准）+ distributed 子命令——集合通信 （环形 allreduce = reduce-scatter + all-gather）、数据并行、ZeRO-1/2、张量并行（含 QKV 按 head 列切分）、 流水线并行（GPipe / 1F1B）、3D 并行规划。实现是单进程模拟 world：语义与数值对齐真实集合通信， 换成 NCCL / MPI 时算法本身无需改动。 与已有代码的衔接：数据并行复用 src/train.rs 的训练循环结构； ZeRO 分片作用于 src/optim.rs 的 AdamW 动量状态（m / v）。

1. 为什么需要分布式训练？

一个 70B 参数的模型，仅权重就需要 140GB（FP16），加上梯度和优化器状态：

组成 大小（FP32 优化器 + FP16 模型）
模型参数（FP16） 140 GB
梯度（FP16） 140 GB
Adam 一阶动量（FP32） 280 GB
Adam 二阶动量（FP32） 280 GB
总计 840 GB

单张 A100 80GB 显存远远不够，必须分布到多张 GPU 上。

2. 三种并行策略

2.1 数据并行（Data Parallelism, DP）

每张 GPU 都有模型的完整副本，但处理不同的数据 batch。

GPU 0: 完整模型 + Batch 0 → grad_0 ─┐
GPU 1: 完整模型 + Batch 1 → grad_1 ─┤→ AllReduce(平均梯度) → 各自更新
GPU 2: 完整模型 + Batch 2 → grad_2 ─┤
GPU 3: 完整模型 + Batch 3 → grad_3 ─┘

AllReduce 操作：所有 GPU 把自己的梯度汇总求平均，每个 GPU 都得到相同的平均梯度。

优点：实现简单，线性加速 缺点：每张 GPU 都要存完整模型，放不下就没法用

2.2 ZeRO（Zero Redundancy Optimizer）

DeepSpeed 提出的优化——把优化器状态、梯度、参数分片到不同 GPU 上：

阶段 分片内容 每 GPU 显存
ZeRO-1 优化器状态 参数 + 梯度 + 优化器/N
ZeRO-2 优化器状态 + 梯度 参数 + (梯度 + 优化器)/N
ZeRO-3 优化器状态 + 梯度 + 参数 (参数 + 梯度 + 优化器)/N 
ZeRO-3 (4 GPUs):
  GPU 0: 参数分片 0-25% + 对应的优化器状态
  GPU 1: 参数分片 25-50% + 对应的优化器状态
  GPU 2: 参数分片 50-75% + 对应的优化器状态
  GPU 3: 参数分片 75-100% + 对应的优化器状态

前向/反向时: 需要哪个参数分片就从对应 GPU 获取（AllGather）
更新时: 只更新自己负责的参数分片

70B 模型在 ZeRO-3 + 8 GPU 上：每 GPU 只需 ~105GB（接近单卡可承载）。

2.3 模型并行（Model Parallelism）

把模型切分到不同 GPU 上——每张 GPU 只负责模型的一部分。

张量并行（Tensor Parallelism, TP）

把单层内的矩阵运算切分到多张 GPU：

线性层 Y = X @ W，W ∈ R^{d × d}
  │
  │ 按列切分 W = [W_1 | W_2]
  │
GPU 0: Y_1 = X @ W_1  ─┐
GPU 1: Y_2 = X @ W_2  ─┤→ 拼接 Y = [Y_1 | Y_2]

注意力层可以按 head 切分（天然并行），FFN 可以按列/行切分。

流水线并行（Pipeline Parallelism, PP）

把模型的不同层放在不同 GPU 上：

GPU 0: Layer 0-7   → 输出传给 GPU 1
GPU 1: Layer 8-15  → 输出传给 GPU 2
GPU 2: Layer 16-23 → 输出传给 GPU 3
GPU 3: Layer 24-31 → 最终输出

问题：朴素实现会导致严重的 GPU 空闲（流水线气泡）。

解决方案——GPipe / 1F1B 调度：

时间 →
GPU 0: [F1][F2][F3][F4]  [B4][B3][B2][B1]
GPU 1:     [F1][F2][F3][F4]  [B4][B3][B2][B1]
GPU 2:         [F1][F2][F3][F4]  [B4][B3][B2][B1]
GPU 3:             [F1][F2][F3][F4]  [B4][B3][B2][B1]

F = Forward, B = Backward
把一个 batch 拆成多个 micro-batch，让 GPU 尽量忙碌

3. 3D 并行

实际大规模训练中，三种并行策略组合使用：

3D 并行 (以 256 GPU 为例):
  数据并行 × 流水线并行 × 张量并行 = 256
  例: DP=8, PP=4, TP=8

  - TP=8: 每层的矩阵运算分布在 8 张 GPU（组内高速互联 NVLink）
  - PP=4: 模型分成 4 个流水线阶段（组间用 InfiniBand）
  - DP=8: 8 组数据并行（组间 AllReduce 梯度）

4. 通信原语

AllReduce

所有 GPU 求和/求平均，每张 GPU 都得到结果。

GPU 0: grad_0 ──┐
GPU 1: grad_1 ──┤→ 平均 → 每张 GPU 都有 avg(grad)
GPU 2: grad_2 ──┤
GPU 3: grad_3 ──┘

实现方式：Ring AllReduce（O(2(N-1)/N × 数据量)），通信量几乎不随 GPU 数量增加。

AllGather

每张 GPU 持有部分数据，AllGather 后每张 GPU 都有完整数据。

GPU 0: [参数 0-25%] ──┐
GPU 1: [参数 25-50%] ─┤→ 每张 GPU 都有 [100% 参数]
GPU 2: [参数 50-75%] ─┤
GPU 3: [参数 75-100%]─┘

ReduceScatter

每张 GPU 有一份完整数据，ReduceScatter 后每张 GPU 只保留对应分片的求和结果。

GPU 0: [完整梯度] ──┐
GPU 1: [完整梯度] ──┤→ GPU 0 得到 [分片0的和]
GPU 2: [完整梯度] ──┤   GPU 1 得到 [分片1的和]
GPU 3: [完整梯度] ──┘   ...

AllReduce = ReduceScatter + AllGather

5. 梯度累积与分布式训练

分布式训练中，有效 batch size 会变得很大：

有效 batch = micro_batch × 梯度累积步数 × GPU 数量

例: micro_batch=4, 梯度累积=8, GPU=32
有效 batch = 4 × 8 × 32 = 1024

太大的 batch 会降低训练质量，需要相应调整学习率：

$$ \text{lr}{\text{new}} = \text{lr}{\text{base}} \times \frac{\text{batch}{\text{new}}}{\text{batch}{\text{base}}} $$

6. 混合精度与分布式

分布式训练几乎总是结合混合精度：

通信阶段: FP16/BF16（减少通信量 2×）
计算阶段: FP16/BF16（利用 Tensor Core 加速）
优化器更新: FP32（保持数值精度）

BF16 vs FP16

格式 指数位 尾数位 范围 精度
FP16 5 10 ±65504 高
BF16 8 7 ±3.4e38 低

BF16 的范围与 FP32 相同，不需要损失缩放（loss scaling），训练更稳定。现代训练几乎都用 BF16。

7. 通信瓶颈与优化

通信量估算

以 ZeRO-3 训练 70B 模型为例：

前向: AllGather 参数 140GB (每层一次，分摊到整个前向)
反向: AllGather 参数 140GB + ReduceScatter 梯度 140GB
总计: ~420GB 通信量 / step

用 NVLink 600GB/s: ~0.7 秒通信
用 InfiniBand 400Gb/s (~50GB/s): ~8.4 秒通信

计算-通信重叠

理想情况:
  [计算层 1]  [计算层 2]  [计算层 3]
  [通信层 0]  [通信层 1]  [通信层 2]  ← 通信与计算重叠

梯度压缩

在数据并行中，AllReduce 梯度时可以用低精度（FP16 甚至 INT8）减少通信量。

9. 本仓库实现要点

上面的原理已全部落地为可运行代码，分两层：

  • src/distributed.rs：单进程模拟（所有 rank 都在一个地址空间里， "通信"就是 memcpy）。它把"切分 → 通信 → 拼回"的每一步都做成可与单卡逐位对拍的算法， 真正容易错的地方（梯度平均对不对、每个 rank 是否真的只持有 1/N 的状态）在这里就能钉死；
  • src/comm.rs：真多进程的传输层（TCP 上的环形集合通信）+ 三维通信组， 以及真数据并行的训练接线。

CLI 入口是 distributed 子命令（跑模拟器）；真多进程训练按下面「启动多进程训练」一节拉进程。

代码地图

真多进程数据并行（DP 接线）

上面那条子命令跑的是单进程模拟：所有 rank 都在一个地址空间里，"通信"退化成 memcpy。 真起 N 个进程时缺的不是算法，而是三件事——传输、数据分片、哪些副作用只能由一个 rank 做。

传输层与三维通信组（src/comm.rs）

每个 rank 一个进程，两两建一条 TCP 连接（全连接拓扑，就是 PyTorch gloo 的 CPU 做法）， 环形 allreduce / reduce-scatter / all-gather / broadcast 每轮只跟真实邻居交换数据。两个设计点：

  • 每条连接配一条独立读线程：环形算法里"先发后收"是常态，收发共用一条阻塞 socket 很容易在环上互相等待到死；读线程永远在把收到的帧塞进内存队列，写满 TCP 缓冲不会卡住环的推进。
  • 帧头带通信组 tag：同一对 rank 可能同时属于 DP 组与 TP 组，按 (来源 rank, 组 tag) 取队首即可（SPMD 保证组内集合调用顺序一致、TCP 保证单连接内有序），不需要全局序号。

进程坐标全部来自环境变量，dp 由 WORLD_SIZE / (DIST_TP × DIST_PP) 推出来：

变量 含义
RANK 全局 rank（0..WORLD_SIZE）
WORLD_SIZE 总进程数，必须等于 dp · tp · pp
LOCAL_RANK 本机内的序号：选 GPU adapter 用（LOCAL_RANK % adapter 数，单卡时全体落到同一张卡）
DIST_TP / DIST_PP / DIST_DP 三个轴的切分；只给 WORLD_SIZE 就是纯数据并行，DIST_DP 只作交叉校验
MASTER_ADDR / MASTER_PORT 建连地址与基准端口（rank r 监听 port + r）

先断言整除、再做除法：除不尽被静默取整的话，dp·tp·pp ≠ world 的错误要拖到第一次集合 通信才以"挂死"（等超时）的形式暴露，排查成本远高于起跑前 panic。

训练接线：四个同步点 + 一个门控

train_transformer 多了最后一个参数 dist: Option<&DistRuntime>，传 None 就是原来的单进程 路径（一行都不变）。接上之后，训练循环里多了四个同步点：

时机 动作 不同步会怎样
采样前 mix_dp_rank 把训练 rng 扰动到与 dp_rank 相关的轨道（splitmix64） 各副本每步抽到同一批数据，梯度平均等于单卡那批的梯度——DP 白跑 N 遍
AMP 反缩放之后、裁剪之前 allreduce_mean_grads：一次拼接好的环形 allreduce 求平均 各副本梯度不同步，模型直接分叉
检测到梯度溢出时 sync_overflow：任一副本溢出 ⇒ 全体按溢出处理（先各自 detect_overflow，再全体 note_overflow） AMP 的 scale 分叉 ⇒ 反缩放系数不同 ⇒ 同一份梯度被除以不同的数
opt.step() 之后 allreduce_mean_moe_bias：取各副本均衡偏置的平均写回 偏置参与下一次前向的硬路由 ⇒ 各副本 val_loss 不同 ⇒ 早停判据分叉 ⇒ 挂死

顺序不是随便定的：梯度平均必须发生在反缩放之后（平均的得是真实尺度的梯度）， 又必须在裁剪之前（阈值要作用在同步后的全局梯度上，才与单卡口径一致）。

评估用的 rng 刻意不扰动：各副本必须在同一批验证数据上评估——这是"早停判据一致"的前提， 而判据一致又是"不会有一半 rank 提前退出集合通信"的前提。同理，控制流一律不按 rank 分支： 所有 rank 都跑评估、都算最优/早停判据。

rank 0 门控只管副作用，不管控制流：运行日志与进度（logln! 在 format! 之前按 runlog::rank_muted() 短路）、指标 CSV、checkpoint 与分词器落盘。N 个副本同时写同一个 tokenizer.json / latest.ckpt / CSV，轻则内容互相覆盖，重则落下一份写了一半的存档。

启动多进程训练

多进程训练没有"一条命令"的写法：必须一次编译 + N 份带不同 env 的进程 + 按退出码判成败。 下面这段可以直接粘进 PowerShell 会话（把 $n 改成进程数即可），不需要任何启动脚本：

# 1) 只编译一次：N 个进程同时 cargo build 会抢 target/ 的锁，且每个都要多付一次 cargo 启动开销
cargo build --release --features gpu

# 2) 目标进程数 + 公共坐标（只给 WORLD_SIZE 就是纯数据并行，dp 自动推导）
$n    = 2
$exe  = '.\target\release\llm_from_scratch.exe'
$utf8 = New-Object System.Text.UTF8Encoding $false
New-Item -ItemType Directory -Force logs | Out-Null

# 3) 逐进程启动：RANK / LOCAL_RANK 各不相同，其它 env 相同
#    用 ProcessStartInfo 按子进程给 env —— 既不用改本会话的环境变量，退出码也可靠可读
$started = @()
for ($r = 0; $r -lt $n; $r++) {
    $psi = New-Object System.Diagnostics.ProcessStartInfo
    $psi.FileName  = $exe
    $psi.Arguments = 'train --config config/dp-smoke.json'
    $psi.WorkingDirectory = (Get-Location).Path
    $psi.UseShellExecute = $false      # 关掉 ShellExecute 才能用 EnvironmentVariables
    $psi.CreateNoWindow  = $true
    $psi.EnvironmentVariables['MASTER_ADDR'] = '127.0.0.1'
    $psi.EnvironmentVariables['MASTER_PORT'] = '29611'
    $psi.EnvironmentVariables['WORLD_SIZE']  = "$n"
    $psi.EnvironmentVariables['DIST_TP']     = '1'
    $psi.EnvironmentVariables['DIST_PP']     = '1'
    $psi.EnvironmentVariables['DIST_DP']     = "$n"
    $psi.EnvironmentVariables['LLM_GPU_STACK'] = '1'
    $psi.EnvironmentVariables['RANK']       = "$r"
    $psi.EnvironmentVariables['LOCAL_RANK'] = "$r"   # 单机：本机序号 = 全局 rank
    if ($r -ne 0) {
        # 其余 rank 被 runlog 静音，输出收进文件；**必须读管道**，不读会把它堵死在写上
        $psi.RedirectStandardOutput = $true
        $psi.RedirectStandardError  = $true
    }
    $p = [System.Diagnostics.Process]::Start($psi)
    if ($r -eq 0) {
        $started += [pscustomobject]@{ Rank = $r; Proc = $p; Out = $null; Err = $null }
    } else {
        $started += [pscustomobject]@{
            Rank = $r; Proc = $p
            Out  = $p.StandardOutput.ReadToEndAsync()
            Err  = $p.StandardError.ReadToEndAsync()
        }
    }
}

# 4) 等全部退出、收日志、按退出码判成败（退出码是唯一判据）
foreach ($e in $started) {
    $e.Proc.WaitForExit()
    if ($e.Out) {
        [System.IO.File]::WriteAllText("logs\dist_rank$($e.Rank).out", $e.Out.Result, $utf8)
        [System.IO.File]::WriteAllText("logs\dist_rank$($e.Rank).err", $e.Err.Result, $utf8)
    }
}
$codes = @($started | ForEach-Object { $_.Proc.ExitCode })
for ($r = 0; $r -lt $n; $r++) { Write-Host "rank $r 退出码 $($codes[$r])" }
if (@($codes | Where-Object { $_ -ne 0 }).Count -gt 0) { throw '有 rank 非零退出' }

三个必须做对的地方（任何一条错了都不会立刻报错，只会"看起来跑完了但结果不对"或干脆卡住）：

  1. 先 build、再直跑 exe：N 个 cargo run 会串行抢 target/ 的锁，而且每个进程都要多付一次 cargo 启动开销（本仓库 release + LTO 约 2 分钟）。
  2. RANK / LOCAL_RANK 是每进程不同的，而 shell 的环境变量是进程级的：要么像上面这样 按子进程注入（推荐——本会话的环境变量从头到尾没被改过，也就不需要还原）， 要么"设置 → 启动 → 改掉 → 再启动"，并在结束时还原。
  3. 判成败只能看子进程退出码，而取退出码本身有坑：PowerShell 5.1 下 Start-Process -PassThru 拿到的 .ExitCode 实测是空值，$null -ne 0 为真 —— 用它判定会把跑得好好的训练误报成"有 rank 非零退出"。所以上面用的是 [System.Diagnostics.Process]::Start。

⚠️ 两个小坑：参数里别加 -- 分隔符（PowerShell 5.1 的绑定器会把单独的 -- 当成 "空参数名"，报 parameter name '' is ambiguous，命令连第一行都没机会执行）， 直接写 --config config/dp-smoke.json 即可；也别用 cargo run 起这 N 个进程， 否则它们又会各自去碰一次 cargo。另外 rank≠0 的输出被 runlog 静音（见上面的「rank 0 门控」）， 所以上面把它们的 stdout/stderr 收进了 logs/dist_rank{N}.out——管道必须读， 不读的话子进程写满管道缓冲就会卡住，整个作业看起来像"挂死"。

config/dp-smoke.json 是一个 4 步就能跑完的小配置（输出到 checkpoints/dp-smoke/）， 适合拿来验证"多进程能不能起来、能不能对齐"，不适合看训练效果。 实测：同一份配置连跑两遍，latest.ckpt 逐字节相同。

⚠️ 目前只支持纯数据并行（DIST_TP = DIST_PP = 1）。TP / PP 的接线（参数分片 + 层内集合通信、层切分 + micro-batch 调度）尚未完成，传 DIST_TP / DIST_PP > 1 会被 进程当场拒绝（cmd_train 里的断言），而不是跑出一个"每个 rank 都拿完整模型"的错结果。

10. 小结与下一课

本课小结

本课覆盖分布式训练的完整拼图：三种并行策略（DP / ZeRO / TP·PP）、集合通信原语、通信量估算与计算-通信重叠。本仓库把原理落成两层代码——src/distributed.rs 的单进程模拟负责"切分 → 通信 → 拼回"的逐位对拍，src/comm.rs 的 TCP 传输层负责把纯数据并行真正跑成多进程。
